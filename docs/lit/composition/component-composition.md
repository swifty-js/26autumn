处理复杂性并将 Lit 代码拆分为独立单元的最常见方式是*组件组合*：即从更小、更简单的组件构建出大型、复杂组件的过程。假设你被要求实现一个 UI 界面：

![一个显示一组动物照片的应用截图。该应用有一个顶部栏，包含标题（"Fuzzy"）和一个菜单按钮。左侧菜单抽屉已打开，显示了一组选项。](/images/docs/composition/fuzzy-screenshot.png)

你大概能识别出哪些区域在实现时会涉及一些复杂性。这些区域很可能就是组件。

通过将复杂性隔离到特定的组件中，你可以让工作变得更加简单，然后将这些组件组合在一起来创建整体设计。

例如，上面这个相当简单的截图涉及了多个可能的组件：一个顶部栏、一个菜单按钮、一个包含用于导航当前部分的菜单项的抽屉；以及一个主内容区域。这些中的每一个都可以用一个组件来表示。一个复杂的组件，比如带有导航菜单的抽屉，可能会被拆分为许多更小的组件：抽屉本身、一个用于打开和关闭抽屉的按钮、菜单、各个菜单项。

Lit 允许你通过向模板添加元素来进行组合——无论是内置的 HTML 元素还是自定义元素。

```js
render() {
  return html`
    <top-bar>
      <icon-button icon="menu" slot="nav-button"></icon-button>
      <span slot="title">Fuzzy</span>
    </top-bar>
    `;
}
```

## 什么是好的组件

在决定如何拆分功能时，有几个要点可以帮助你识别何时应该创建新组件。如果以下一项或多项适用，那么一段 UI 可能就是组件的良好候选：

- 它有自己的状态。
- 它有自己的模板。
- 它在多个地方被使用，无论是在当前组件中还是在多个组件中。
- 它专注于一件事并做好。
- 它有明确定义的 API。

像按钮、复选框和输入字段这样的可复用控件可以成为很好的组件。但更复杂的 UI 部分，如抽屉和轮播图，也是组件化的良好候选。

## 在树中上下传递数据

在与子组件交换数据时，一般规则是遵循 DOM 的模型：_属性向下_，_事件向上_。

- 属性向下。在子组件上设置属性通常比调用子组件的方法更可取。在 Lit 模板和其他声明式模板系统中设置属性很容易。

- 事件向上。在 Web 平台中，触发事件是元素向树的上方发送信息的默认方式，通常是为了响应用户交互。这让宿主组件可以响应事件，或者转换并重新触发事件以传递给树中更上层的祖先组件。

这个模型有一些含义：

- 组件应该是其 shadow DOM 中子组件的真实数据来源。子组件不应该在其宿主组件上设置属性或调用方法。

- 如果组件更改了自身的公共属性，它应该触发一个事件来通知树中更上层的组件。通常这些更改是用户操作的结果——比如按下按钮或选择菜单项。想想原生的 `input` 元素，当用户更改输入值时会触发一个事件。

考虑一个菜单组件，它包含一组菜单项，并将 `items` 和 `selectedItem` 属性作为其公共 API 的一部分公开。它的 DOM 结构可能如下所示：

![表示菜单的 DOM 节点层次结构。顶层节点 my-menu 有一个 ShadowRoot，其中包含三个 my-item 元素。](/images/docs/composition/composition-menu-component.png){.light-bg}

当用户选择一个项目时，`my-menu` 元素应该更新其 `selectedItem` 属性。它还应该触发一个事件来通知任何拥有该组件的组件选择已更改。完整的顺序大致如下：

- 用户与一个项目交互，导致触发一个事件（要么是像 `click` 这样的标准事件，要么是 `my-item` 组件特有的某个事件）。
- `my-menu` 元素获取该事件，并更新其 `selectedItem` 属性。它还可能更改一些状态以使被选中的项目高亮显示。
- `my-menu` 元素触发一个语义化事件，表明选择已更改。例如，这个事件可能叫做 `selected-item-changed`。由于这个事件是 `my-menu` API 的一部分，它在该上下文中应该具有语义上的意义。

有关分发和监听事件的更多信息，请参阅[事件](/docs/v3/components/events/)。

## 跨树传递数据

属性向下和事件向上是一个很好的起步规则。但如果你需要在两个没有直接后代关系的组件之间交换数据呢？例如，在 shadow 树中是兄弟关系的两个组件？

解决这个问题的一种方法是使用*中介者模式*。在中介者模式中，对等组件之间不直接通信。相反，交互由第三方进行*中介*。

实现中介者模式的一种简单方式是让拥有组件处理来自其子组件的事件，然后通过将更改的数据沿树向下传递回来，按需更新其子组件的状态。通过添加一个中介者，你可以使用熟悉的事件向上、属性向下原则来跨树传递数据。

在下面的示例中，中介者元素监听其 shadow DOM 中输入和按钮元素的事件。它控制按钮的启用状态，这样用户只有在输入中有文本时才能点击"提交"。

## Light DOM 子节点

除了 shadow DOM 中的节点之外，你还可以渲染由组件使用者提供的子节点，就像标准的 `<select>` 元素可以接受一组 `<option>` 元素作为子节点并将它们渲染为菜单项一样。

子节点有时被称为"light DOM"，以区别于组件的 shadow DOM。例如：

```html
<top-bar>
  <icon-button icon="menu" slot="nav-button"></icon-button>
  <span slot="title">Fuzzy</span>
</top-bar>
```

这里 `top-bar` 元素有两个由用户提供的 light DOM 子节点：一个导航按钮和一个标题。

与 light DOM 子节点的交互方式不同于与 shadow DOM 中节点的交互方式。组件 shadow DOM 中的节点由组件管理，不应从组件外部访问。Light DOM 子节点由组件外部管理，但组件也可以访问它们。组件的使用者可以随时添加或删除 light DOM 子节点，因此组件不能假设有一组静态的子节点。

组件可以控制子节点是否被渲染以及在哪里渲染，方法是在其 shadow DOM 中使用 `<slot>` 元素。它还可以通过监听 `slotchange` 事件来接收子节点被添加和删除的通知。

有关更多信息，请参阅[使用插槽渲染子节点](/docs/v3/components/shadow-dom/#slots)和[访问插槽中的子节点](/docs/v3/components/shadow-dom/#accessing-slotted-children)部分。
