# IEG 工作 2: 内存泄漏排查、进程池与 ffi 内存模型

## 背景

IEG 的 NoSQL 管理端中, 表文件的格式是 xml, Koa 后端需要对这些文件做解密和解析. 解密与解析逻辑由 C++ 实现并编译成 .so 动态链接库, JS 侧通过 ffi-napi 调用. 这段工作有三条主线:

- 使用 valgrind 排查发现 C++ 侧 protobuf 的使用存在内存泄漏
- 为了避免解密、解析 xml 时崩溃 (例如 segfault) 影响主 Koa 进程, 使用 generic-pool 编写进程池, 把 .so 调用隔离到子进程
- 每次解析 xml 都需要创建一个大对象 (该对象的部分属性是一块大 buffer), 基于 V8 隐藏类创建对象池, 降低 Koa 服务的 GC 压力

下面按考点逐个展开.

## 进程池、线程池的常用参数

无论进程池还是线程池, 参数模型基本一致, 以本项目使用的 generic-pool 为例:

- max: 池中 worker (进程/线程) 的数量上限. 决定并发处理能力的天花板
- min: 池常驻的最小数量. 进程池启动成本高 (fork 进程、加载 .so、初始化运行时), min 设为大于 0 可以避免冷启动毛刺
- acquireTimeoutMillis: 从池中获取 worker 的等待超时. 池满且排队超过该时间就抛错, 避免请求无限堆积; 上层要处理这个错误并给用户降级提示
- maxWaitingClients: 排队等待队列的上限, 和 acquireTimeout 一起构成背压机制
- idleTimeoutMillis: worker 空闲多久后被回收 (数量高于 min 的部分). 解析任务是突发型流量, 空闲回收可以释放内存
- evictionRunIntervalMillis / numTestsPerEvictionRun: 空闲驱逐检查的周期和每次检查的数量
- testOnBorrow / testOnReturn: 借出/归还时是否做健康检查. 进程池场景可以检查子进程是否还存活, 避免把已经崩溃的进程借给调用方
- fifo: 是否按先进先出复用空闲 worker

参数调优的思路:

- max 怎么定: 解密、解析是 CPU 密集型任务, 线程池的 max 通常参考 CPU 核数 (例如核数或核数 + 1); 进程池还要叠加内存约束, 每个子进程都独立加载 .so、持有解析 buffer, max 太大会把机器内存吃满, 需要按 单进程峰值内存 x max 估算
- min 怎么定: 看流量形态. 持续有请求就常驻 min 个进程避免冷启动; 明显有波峰波谷就让 min 小一些配合 idleTimeout 回收
- 超时怎么定: acquireTimeout 要大于单次解析的 P99 耗时, 否则正常慢请求会被误杀; 同时不能大到让调用方无限等待

进程池与线程池的选型差异, 也是本项目的关键决策:

- 线程池 (Node 侧对应 worker_threads) 共享进程地址空间, 通信快、开销小, 但任何一个线程里的 C++ 代码崩溃 (segfault、abort) 都会带走整个进程
- 进程池每个 worker 有独立地址空间, 子进程崩溃只影响自己, 主 Koa 进程感知到退出后销毁该 worker、重建新进程即可, 服务整体不受影响
- 本项目 .so 是第三方 C++ 代码, 存在内存泄漏这类不稳定因素, 崩溃隔离的收益大于进程间通信的开销, 所以选进程池

配套的 JS 侧对象池设计:

- 每次解析都要创建一个大对象 (部分属性是大 buffer), 高频创建会让 V8 频繁触发 GC, 大对象直接进入老生代, 回收代价高
- 做法是对象池: 预创建一批解析上下文对象, 用完重置状态后归还复用, 避免反复分配大 buffer
- 基于 V8 隐藏类 (hidden class / map) 的考虑: V8 对结构稳定的对象会生成相同的隐藏类, 属性访问走内联缓存, 速度快; 对象池里的对象保持相同的属性添加顺序和结构 (单态), 不动态增删属性, 既让访问快, 也让对象大小固定、复用安全

## valgrind 的原理、如何使用 valgrind 排查

valgrind 是一个动态分析框架, 最常用的是 memcheck 工具, 用于排查内存错误和内存泄漏.

原理:

- valgrind 采用动态二进制插桩 (dynamic binary instrumentation): 不修改源码、不需要重新编译, 程序运行在 valgrind 的虚拟 CPU 上, valgrind 在程序加载时把机器指令逐段翻译、插入检查代码后再执行
- memcheck 为程序的每一个内存字节维护两份影子状态: 该字节是否可寻址 (addressable, 即是否属于合法分配的内存), 以及该字节的值是否已定义 (defined). 所有内存读写指令都被插桩检查这两个状态
- 基于这套机制可以检测: 读写已释放的内存 (use after free)、越界读写、使用未初始化的值、new/delete 与 malloc/free 不匹配, 以及内存泄漏
- 泄漏检测的原理: 程序退出前, memcheck 扫描所有寄存器、栈和全局数据中仍然指向堆内存的指针, 把堆块分类:
  - definitely lost: 没有任何指针指向这块内存, 确定泄漏
  - indirectly lost: 指向它的内存本身也泄漏了
  - possibly lost: 指针指向块内部而不是块起始 (常见于数组或内部指针), 疑似泄漏
  - still reachable: 仍有指针可达, 通常不算问题 (很多库的全局对象属于这类)
- 代价: 插桩执行比原生慢一个数量级以上, 内存占用也显著增加, 适合定向排查, 不适合常态运行

使用方式:

```sh
# 直接跑 node 进程 (ffi-napi 加载的 .so 在同一进程内, 会被一起插桩)
valgrind --tool=memcheck \
  --leak-check=full \
  --show-leak-kinds=definite,possible \
  --track-origins=yes \
  --log-file=valgrind.log \
  node parse-xml.js

# 更干净的做法: 用 C++ 写一个最小复现程序, 只走 protobuf 解析路径
valgrind --leak-check=full --track-origins=yes ./parse_test table.xml
```

排查步骤, 以本项目为例:

1. 构造最小输入: 准备一份典型的 xml 表文件, 写一个只调用 .so 解密 + protobuf 解析的入口, 减少 Node 自身的噪音
2. 跑 valgrind 拿到报告: 关注 definitely lost 的条目, 每条都带分配点的调用栈
3. 读调用栈定位分配点: 报告的栈会指向 protobuf 内部的 Allocate 路径, 结合 C++ 侧代码确认是哪类对象没有释放. 本项目最终定位到 C++ 侧 protobuf 的使用问题: 解析产生的 message 对象在部分路径上没有正确释放, 每次解析都漏一点, 长时间运行后进程内存持续增长
4. 用 suppression 过滤无关噪音: Node、glibc 等运行时的已知泄漏可以写进 suppression 文件, 让报告聚焦业务代码
5. 修复后复测: 同样的输入再跑一遍, 确认 definitely lost 归零; 再长跑观察 RSS 是否稳定

补充对比: 如果能改 C++ 源码并重新编译, AddressSanitizer (ASan) 是更快的替代方案, 运行时开销远小于 valgrind, 但需要带 -fsanitize=address 重新构建; valgrind 的优势是零编译、对现成的 .so 二进制直接可用, 本项目排查第三方 .so 时这个特性很关键.

## ffi-napi 调用 .so: 是否共享内存, 该内存受 JS GC 控制吗

先说结论: 分情况. 标量参数是拷贝, 不共享; Buffer 和指针参数是共享内存; JS GC 只能管理 JS 侧分配的内存, C++ 侧分配的内存不受 JS GC 控制.

ffi-napi 的调用机制:

- ffi-napi 底层基于 libffi. JS 侧声明 C 函数签名 (参数类型、返回类型), ffi-napi 通过 dlopen 加载 .so、dlsym 找到符号, 调用时按 ABI 把参数组装成 C 能理解的布局再跳转执行
- 标量类型 (int、double 等): 调用时按值拷贝进寄存器/栈, C++ 侧拿到的是副本, 两边互不影响, 不存在共享

Buffer / 指针场景, 是真正的共享内存:

- JS 把 Buffer 传给 C++ 函数时, 传的是这块内存的地址, C++ 侧直接在这块内存上读写, 零拷贝; C++ 写入的内容 JS 侧立刻可见, 这正是解密、解析这类场景需要的: JS 分配 buffer, C++ 原地写入解析结果
- 共享带来两个必须注意的问题:
  - 生命周期: C++ 侧如果只在同步调用期间使用这块内存, 是安全的; 如果 C++ 把指针存下来异步使用, 而 JS 侧已经没人引用这个 Buffer, GC 可能回收它, C++ 侧就拿到悬垂指针. 规避方式是 JS 侧保持引用直到 C++ 用完, 或者 C++ 侧同步拷贝走
  - 小 Buffer 的池化陷阱: Node 对小于 4KB 的 Buffer 可能从共享的 Buffer.poolSize 内存池里切片分配, 把这种切片的地址交给 C++ 有越界读写相邻数据的风险; 传给 native 的 buffer 建议用 Buffer.allocUnsafeSlow 或确保独立分配

C++ 侧分配的内存, 不受 JS GC 控制:

- 如果 .so 内部用 malloc/new 分配内存 (例如 protobuf 解析出的 message), 把指针返回给 JS, 这块内存完全在 V8 堆外, JS GC 看不见它、不会回收它
- 唯一的释放途径是 JS 侧显式再调一次 .so 提供的释放函数 (例如 destroy_message), 用 ffi 声明这个函数并在用完后调用
- 实践中可以用 try/finally 保证释放一定执行; 也可以用 FinalizationRegistry 在 JS 包装对象被 GC 时触发释放, 但 GC 时机不可控, 只能作为兜底, 不能作为主要手段
- 如果忘了释放, 表现就是 Node 进程 RSS 持续增长但 V8 堆内存正常, 这类泄漏要用 valgrind/ASan 在 native 侧排查, 用 heap snapshot 是查不到的

和本项目的呼应:

- 内存泄漏排查一节里, C++ 侧 protobuf 的泄漏正是这类"堆外内存不受 JS GC 管理"的典型: JS 侧看 GC 指标一切正常, 进程内存却在涨, 只能靠 valgrind 定位到 native 分配点
- 这也是选择进程池的另一个理由: 堆外泄漏和崩溃都发生在子进程里, 最坏情况下重启子进程就能恢复, 主 Koa 进程的内存曲线保持稳定

## 后续迁移到 C++ Addon: 优势与 tradeoff

ffi-napi 方案跑通之后, 随着解析调用量和数据量上升, 评估并迁移到了 C++ Addon (基于 N-API / node-addon-api) 的方案. 两者的定位差异决定了这次迁移的收益和代价.

C++ Addon 的优势:

- 调用开销更低: ffi-napi 每次调用都要经过 libffi 做运行时的参数组装 (JS 值 -> C ABI 布局), 类型转换全靠运行时描述; Addon 直接通过 N-API 读写 JS 值, 没有这层中间转换, 高频调用场景下差距明显
- 大数据零拷贝更自然: Addon 可以直接接收 ArrayBuffer 并在 C++ 侧原地处理, 解析结果也可以包成 external buffer 返回, 不需要像 ffi 那样围绕裸指针手工管理
- 内存管理可以和 GC 联动: N-API 支持给 external 内存挂 finalize 回调, JS 侧包装对象被 GC 回收时自动触发 C++ 侧释放. 这直接改善了 ffi 方案里"C++ 分配的内存不受 JS GC 控制, 只能手动释放"的问题, 堆外内存泄漏的敞口变小
- 异步能力完整: CPU 密集的解析可以用 AsyncWorker 丢进 libuv 线程池执行, 不阻塞事件循环; 跨线程回传结果有 ThreadSafeFunction 兜底. ffi-napi 的异步支持弱, 之前只能靠进程池顺带解决阻塞问题
- 类型表达更强: 可以直接在 C++ 侧构造 JS 对象、数组返回, 不用把 protobuf message 序列化成 buffer 再在 JS 侧二次解析, 省一次编解码
- ABI 稳定: N-API 保证跨 Node 版本 ABI 兼容, Addon 不需要跟随 Node 小版本反复重编 (这是老式 NAN addon 的痛点)

迁移的 tradeoff, 即 Addon 相比 ffi-napi 付出的代价:

- 编译与分发成本: ffi-napi 是纯 JS 层 + dlopen, 拿来即用; Addon 要走 node-gyp 构建, CI 需要维护编译工具链, 多平台、多 Node 版本要产出对应的 prebuild 产物, 发布链路明显变重
- 迭代耦合: .so 更新只需要替换二进制, JS 侧无感; Addon 的接口变更要同时改 C++ 和 JS 两侧, 并重新编译发布, 迭代节奏被绑在一起
- 崩溃隔离并没有被解决: 这是最容易误判的一点. Addon 运行在 Node 主进程地址空间内, C++ 侧 segfault 依然会带走整个进程. 所以迁移到 Addon 之后, 进程池的隔离层仍然保留, Addon 跑在池内的子进程里. Addon 解决的是性能和内存管理问题, 进程池解决的是故障隔离问题, 两者是叠加关系而不是替代关系
- 开发与调试门槛: 需要团队掌握 N-API 的引用计数、handle scope、ThreadSafeFunction 等概念, native 崩溃的排查依然要靠 valgrind/ASan 这套工具链

一句话总结这次迁移: ffi-napi 适合"快速接入一个现成的 .so、调用量不大"的阶段; 当调用频率、数据体积上来, 且希望堆外内存与 GC 联动时, N-API Addon 是更合适的形态; 而无论用哪种绑定方式, 第三方 C++ 代码的崩溃风险都要靠进程池兜底.
