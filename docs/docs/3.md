# rpc 是什么, rpc 的优势是什么

## rpc 是什么

rpc (Remote Procedure Call, 远程过程调用) 是一种进程间通信方式: 调用方像调用本地函数一样调用另一台机器上服务的方法, 底层的网络传输、序列化、服务寻址等细节对业务代码透明.

例如后端提供一个查询设备性能排行榜的方法, BFF 层的代码写起来是:

```ts
const ranking = await client.getDeviceRanking({ model, page });
```

看起来是本地函数调用, 实际上参数被序列化后通过网络发给后端服务, 后端执行后把结果序列化传回, BFF 拿到反序列化后的结果. "远程调用伪装成本地调用"就是 rpc 的核心思想.

## 一次 rpc 调用的完整流程

1. 服务提供方用 IDL (接口描述语言, 例如 Thrift、Protobuf) 定义服务接口: 方法名、入参、出参的数据结构
2. 代码生成工具根据 IDL 生成服务端骨架 (skeleton) 和客户端存根 (stub)
3. 调用方调用客户端存根的方法, 存根把入参按协议序列化成二进制字节流
4. 字节流通过网络传输 (通常是长连接 + 连接多路复用) 发送到服务端
5. 服务端收到字节流, 反序列化成参数对象, 根据方法名分发到真正的业务实现
6. 业务执行完成, 结果按相反方向序列化、传输、反序列化, 返回给调用方

对调用方来说, 整个 3-6 步都被存根封装掉了, 代码层面只看到一次函数调用.

## rpc 的优势

- 契约先行, 类型安全: 接口由 IDL 定义, 是前后端 (服务间) 的强类型契约; 从 IDL 自动生成客户端代码, 字段改名、类型变更在编译期就能发现, 不需要人工对齐 JSON 文档
- 序列化性能好: Thrift、Protobuf 等二进制协议比 JSON 体积更小、编解码更快, 对高频内部调用尤其明显
- 长连接与连接复用: rpc 框架通常维护连接池, 一次建连后复用, 避免每次请求都走 TCP 建连、TLS 握手的开销; 单连接上还可以多路复用多个请求
- 内置服务治理: 服务注册与发现 (调用方不需要硬编码地址)、负载均衡、超时与重试、熔断限流、链路追踪等能力由框架统一提供, 业务代码不用重复造轮子
- 调用语义清晰: 方法级别的调用模型比"拼 URL + 约定 JSON 结构"更贴近业务代码的表达方式, 重构友好

## rpc 与 http 接口的对比

| 维度     | rpc (如 Kitex + Thrift)             | http + json                                     |
| -------- | ----------------------------------- | ----------------------------------------------- |
| 接口契约 | IDL 定义, 代码生成, 强类型          | 依赖文档或 OpenAPI, 约束较弱                    |
| 序列化   | 二进制, 体积小, 编解码快            | 文本 JSON, 可读性好但体积大                     |
| 连接模型 | 长连接 + 连接池, 复用由框架统一管理 | HTTP/1.1 默认 keep-alive, HTTP/2 长连接多路复用 |
| 服务治理 | 框架内置注册发现、负载均衡、熔断    | 需要网关或自建                                  |
| 通用性   | 多用于内部服务间调用                | 浏览器、开放 API 通用                           |
| 调试     | 需要专用工具                        | curl 即可, 调试直观                             |

两者不是替代关系: 内部服务间高频调用适合 rpc; 面向浏览器、第三方开放接口适合 http.

## ToD 项目中的 rpc 实践

ToD 项目的后端使用 Golang 和字节后端框架 Kitex 对外提供 rpc 服务. 接口用 Thrift IDL 定义, 团队把 Thrift 定义生成 npm 包提供给 BFF 层消费: BFF (Nest.js) 直接 import 生成的客户端代码调用后端 rpc 方法, 入参出参都有 TypeScript 类型, 后端接口变更时 BFF 在编译期就能感知.

这条链路上 rpc 的收益具体体现为:

- 后端的数据服务不止 ToD 前端一个消费方, 其他团队也通过 rpc 接口消费同一份能力, rpc 的契约模型让多消费方接入成本一致
- 设备性能数据查询 QPS 高, 二进制序列化和长连接降低了单次调用的开销
- BFF 与后端分属不同进程、不同语言运行时, IDL 生成的代码保证了两端的类型一致性

BFF 拿到 rpc 返回的数据后做清洗、整形, 再暴露 http 接口给前端页面渲染设备性能排行榜.
