# IEG 工作 4: 排查闭包引用导致的内存泄漏

## 背景

IEG 的 NoSQL 管理端在长时间运行后, Node 服务的堆内存持续缓慢增长, 不随 GC 回落. 排查后定位到闭包引用导致的内存泄漏: 一些函数闭包捕获了大对象的引用 (例如解析后的 xml 表数据、请求上下文), 而这些闭包被定时器、事件监听或长生命周期结构持有, 导致大对象永远可达、无法被 GC 回收.

## 闭包为什么会导致内存泄漏

先讲清楚机制:

- JS 的函数在创建时会捕获它所在作用域的变量引用, 形成闭包. V8 中体现为函数对象上挂着一个 context/scope 链, 指向它引用的外层变量集合
- V8 的 GC 是标记-清除 (mark and sweep): 从 GC roots (全局对象、执行栈、活跃的内部结构) 出发标记所有可达对象, 不可达的才回收
- 闭包本身只要被引用, 它捕获的变量就保持可达. 也就是说: 不是"对象被闭包引用"有问题, 而是"闭包被长生命周期的东西引用, 且闭包捕获了不该长期持有的大对象"

泄漏的成立需要两个条件同时满足:

1. 闭包捕获了大对象 (或会持续增长的结构)
2. 闭包被长生命周期的载体持有, 例如: 未清理的 setInterval/setTimeout、未移除的事件监听器、挂到全局或模块级变量上的回调、没有淘汰策略的缓存

只满足其一不会泄漏: 闭包捕获了大对象但闭包本身很快不可达, GC 正常回收; 闭包长期存活但只捕获小标量, 也没有实际影响.

## 典型泄漏模式

结合本项目和 Node 服务常见场景:

1. 定时器持有闭包

```js
// 泄漏: 定时器没有清理, 闭包一直活着, capturedData 永远可达
function startReport(capturedData) {
  setInterval(() => {
    report(capturedData.summary);
  }, 60_000);
}
```

2. 事件监听器未移除

```js
// 泄漏: 每次请求都注册监听, 从不 off/removeListener,
// 监听回调的闭包累积, 每个都捕获了当次请求的 ctx
emitter.on("refresh", () => {
  doSomething(ctx.parsedTable);
});
```

3. 闭包意外捕获大作用域

```js
function handle(hugeXml) {
  const parsed = parseXml(hugeXml); // 大对象
  registerCallback(() => {
    // 闭包只需要 tiny, 但 V8 的 scope 共享机制下,
    // 同一作用域里被其他闭包引用的 parsed 也可能被一并保留
    log(tiny);
  });
}
```

V8 会对同一作用域的变量做 context 共享: 只要该作用域里有任何一个变量被某个存活闭包引用, 整个 context 对象都可能被保留, 导致"闭包明明只用了小变量, 大对象却也漏了".

4. 缓存只进不出

```js
// 泄漏: Map 挂在全局, 闭包写入后没有任何淘汰路径
const cache = new Map();
function load(key, bigValue) {
  cache.set(key, bigValue);
}
```

5. 被遗忘的全局引用: 调试时把大对象挂到 global 或模块顶层变量, 上线后没有移除.

## 排查手段

1. 确认现象: 区分堆内泄漏还是堆外泄漏

- 用 process.memoryUsage() 观察 heapUsed 与 rss: heapUsed 持续涨说明是 V8 堆内问题 (闭包泄漏属于这类); rss 涨而 heapUsed 平稳则要往 native 侧查 (参考工作 2 的 valgrind 排查)

2. heap snapshot 三次快照对比法 (核心手段)

- 在 Chrome DevTools (node --inspect 连接) 或 memwatch-next、heapdump 这类堆分析工具里:
  - 快照 1: 服务稳定后拍一次
  - 执行可疑操作 N 次 (例如反复触发解析 xml 的请求)
  - 快照 2: 再拍一次
  - 手动触发 GC 后拍快照 3
- 用 Comparison 视图对比快照 1 和快照 3, 只看 "New" (新增且未被回收) 的对象; 泄漏的对象会成批出现
- 选中可疑对象看 Retainers (保留链): 保留链会一路指到 GC root, 闭包泄漏的保留链典型形态是 Object -> (closure) -> Function -> 某个全局的定时器/监听器/Map. 保留链的终点就是修复的入口

3. 定位闭包的捕获内容

- 在 snapshot 里 Function 节点可以看到它关联的 context 对象, 展开能看到闭包实际捕获了哪些变量, 确认是不是意外捕获了大对象

4. 辅助手段

- node --inspect-brk + Allocation instrumentation on timeline: 观察分配随时间累积的曲线, 适合定位"哪个操作路径在持续分配"
- 生产环境不方便接 DevTools 时, 可以周期性打 heapUsed 指标, 结合发布变更记录二分定位引入泄漏的版本

## 修复方式

按泄漏模式对症:

- 定时器: 保存句柄, 在明确的生命周期点 clearInterval/clearTimeout; 服务类对象要有 dispose 语义
- 事件监听: 注册和移除成对出现; Node 侧可以用 { once: true } 或 AbortController 统一管理移除
- 缓存: 加淘汰策略, 容量上限用 lru (参考 ToD 项目的 lru 实现), 或键是对象时改用 WeakMap, 让条目随键的回收自动消失
- 缩小闭包捕获面: 把大对象的使用收敛到局部, 注册回调前把需要的字段提取成小变量, 避免闭包拖着整个大作用域; 必要时把注册逻辑拆到独立函数, 切断与大作用域的联系
- 全局引用: 代码审查中禁止随手挂全局, 调试代码不进主干

修复后用同样的三次快照法复测: 执行 N 次操作后, Comparison 视图里不应再有该类型的 New 对象残留, heapUsed 曲线恢复锯齿形 (涨后被 GC 拉回).

## 与其他工作的关联

- 和工作 2 的区别: 工作 2 是 C++ 侧 protobuf 的堆外泄漏, RSS 涨而 heapUsed 平稳, 用 valgrind 排查; 本工作是 JS 堆内的闭包泄漏, heapUsed 涨, 用 heap snapshot 排查. 判断泄漏先分清在哪个堆
- 和函数组件迁移 (工作 1) 的关联: React 侧的闭包泄漏同样常见, useEffect 里注册的监听、定时器如果不在清理函数里释放, 组件卸载后闭包依然存活; 这也是迁移规范里要求严格检查清理函数的原因
