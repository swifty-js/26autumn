# 为什么要引入 BFF 层

## 背景两条链路的对比

ToD 项目实际的链路是:

```
数据库 -> 后端 (Go + Kitex) -> rpc -> 前端 BFF (Nest.js) -> http -> 前端页面 (React)
```

一个自然的疑问是: 为什么不省掉 BFF, 让后端直接暴露 http 接口给前端页面:

```
数据库 -> 后端 (Go + Kitex) -> http -> 前端页面 (React)
```

省掉一跳看起来更简单, 但在 ToD 这个场景下会带来三个问题: 后端接口被单一前端绑架、前端拿到的是未经加工的大块原始数据、渲染性能和首屏性能受损。下面从这三个角度展开。

## 原因一后端服务有多个消费方-rpc-接口要保持通用

后端的数据服务不是只服务 ToD 前端一个消费方, 其他团队也会通过 rpc 接口消费同一份设备性能数据能力。这决定了后端接口的形态:

- 后端 rpc 接口必须面向"数据能力"设计: 返回通用的、完整的、结构稳定的数据模型, 不能为某一个前端页面的展示需求定制字段
- 如果让后端直接出 http 接口给页面, 后端就要为这个页面写一套视图定制的接口; 明天另一个前端页面接入, 又要再加一套, 后端接口会随消费方数量膨胀, 且每套都耦合具体 UI
- 把"面向页面的适配"收敛到 BFF: 后端只维护一套通用 rpc 接口, 每个前端在各自的 BFF 里做适配, 后端接口变更时, 通过 Thrift IDL 生成的 npm 包在编译期就能被 BFF 感知, 影响面也可控

一句话: rpc 层解决"多个消费方如何共用一份后端能力", BFF 层解决"每个前端如何按自己的需要消费这份能力"。

## 原因二数据清洗与整形

后端 rpc 返回的是通用数据模型, 和页面真正要渲染的视图模型之间有明显差距, 这部分加工工作放在 BFF:

- 字段裁剪与重命名: 通用模型字段多、命名面向数据域, 页面只需要其中一部分; BFF 裁剪后前端拿到的就是干净的视图模型
- 多接口编排: 一个页面往往需要组合多个 rpc 方法的结果 (例如排行榜数据 + 筛选维度配置 + 机型维表), BFF 可以并行调用后聚合成一次 http 响应, 前端不用发多个请求再自己拼
- 格式转换与派生计算: 例如时间戳转展示格式、性能分分档、环比变化计算等, 这些是展示逻辑, 放后端污染通用接口, 放前端则每个页面重复实现
- 变更隔离: 后端数据模型调整时, 只需要改 BFF 的适配层, 前端页面无感; 反过来页面改版需要新字段组合, 也只改 BFF, 不动后端

ToD 项目中 BFF 层 (Nest.js) 调用后端提供的 rpc 方法, 清洗数据后暴露 http 接口给前端, 正是这个分工。

## 原因三海量-android-设备数据下的前端渲染性能

ToD 的数据源是海量 Android 设备上报的性能数据, 即使经过聚合, 排行榜、明细列表的数据量依然很大。BFF 在"控制下发给前端的数据量"上起关键作用:

- 服务端分页: BFF 按页向 rpc 取数, 一次 http 响应只下发当前页需要的条目, 而不是把全量数据推给浏览器
- 预聚合与降采样: 趋势图这类场景, BFF 可以把细粒度数据聚合成前端绘图需要的粒度 (例如按天、按机型分桶), 下发的点数从几十万降到几百
- 就近缓存: BFF 可以缓存加工后的结果 (配合后端的多层缓存), 高频页面的 http 响应直接从缓存出, 减少 rpc 调用和重复计算
- 减小传输体积: 裁剪字段 + 聚合之后, http 响应体显著变小, 下载和 JSON.parse 的耗时都下降

这些手段共同保证了前端侧的渲染性能: 前端拿到的数据量被控制在"刚好够渲染"的规模, 再配合虚拟滚动列表只渲染可视区域内的行, 设备性能排行榜这种长列表才能流畅滚动。如果把后端 http 直连页面, 这些加工要么缺失, 要么被迫塞进后端通用接口或前端组件里, 两边都会被污染。

## 其他收益

除了上面三个主因, BFF 还带来:

- 协议适配: 浏览器只会说 http, 不会直接调 rpc; BFF 承担了 rpc -> http 的协议转换, 后端不需要为浏览器场景维护一套 http 服务
- 语言与团队分工: 后端是 Go 技术栈, 前端团队用 Node (Nest.js) 写 BFF, 数据加工逻辑由更贴近页面的团队维护, 迭代不需要排后端的发布窗口
- 安全边界: 内部 rpc 服务不直接暴露给浏览器, 面向公网的只有 BFF 的 http 接口, 鉴权、限流等可以在 BFF 统一处理

## BFF-的成本与边界

引入 BFF 不是免费的, 面试中也应该主动讲清楚代价:

- 多一跳网络与一次序列化/反序列化, 链路延迟增加
- 多一个服务要部署、监控、排障, 出问题时要区分是 BFF 还是后端的锅
- 如果 BFF 里沉淀了过重的业务逻辑, 会变成第二个后端, 职责失控

所以 BFF 的定位应该克制: 只做面向前端的适配 (编排、清洗、整形、缓存、协议转换), 核心业务逻辑和数据一致性仍然留在后端。ToD 的分工符合这个边界: 后端负责数据服务和 rpc 能力, BFF 只做加工和暴露 http。

## 小结

回到最初的问题, 不采用"数据库 -> 后端 -> http -> 前端页面"的直连方案, 是因为:

- 后端能力有多个消费方, 必须用通用 rpc 接口对外, 不能被单一前端的视图需求绑架
- 通用数据模型到页面视图模型之间的清洗、整形、编排工作, 需要一个专门的适配层承接
- 海量设备数据必须先在服务端做分页、聚合、裁剪, 前端才有渲染性能可言

BFF 就是这个适配层: 对上消费 rpc, 对下提供为页面定制的 http 接口。
