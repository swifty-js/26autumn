# IEG 工作 3: TCP 连接池与连接异常处理

## 背景

IEG 的 NoSQL 管理端需要与 Tencent NoSQL DB Admin 通信, 协议是 TCP 长连接。Koa 后端使用 generic-pool 编写 TCP 连接池来管理与 DB Admin 的连接: 请求到来时从池中借出一条连接, 用完归还复用, 避免每次请求都走建连、握手、认证的完整流程。

连接池的价值:

- 省建连成本: TCP 三次握手加上 DB Admin 侧的认证握手, 每次现建连都是毫秒级开销, 高频请求下累积明显
- 控制连接数量: DB Admin 对单个来源的连接数有限制, 连接池把并发连接数收敛到 max 以内, 不会把对端打满
- 复用与预热: 常驻连接 (min) 让请求直接命中热连接, 延迟稳定

但 TCP 长连接不是"建好就永远可用"的, 连接池的核心难点正是异常处理: 连接失败、超时、对端主动关闭、静默断开, 每一种都要有明确的处理策略。

## 连接池的基本模型

generic-pool 围绕一个 factory 工作, factory 定义连接的生命周期:

```ts
const factory = {
  // 创建一条到 DB Admin 的连接: 建连 + 认证握手
  create: async () => {
    const conn = await connectToDBAdmin({ host, port, connectTimeout });
    await conn.handshake(auth);
    conn.on("error", onError); // 挂上错误监听, 避免未捕获错误打崩进程
    conn.on("close", onClose);
    return conn;
  },
  // 销毁连接: 彻底关闭 socket, 释放文件描述符
  destroy: async (conn) => {
    conn.destroy();
  },
  // 借出前校验连接是否可用 (testOnBorrow 开启时调用)
  validate: async (conn) => {
    return conn.alive && (await conn.ping(pingTimeout));
  },
};

const pool = genericPool.createPool(factory, {
  max: 10, // 连接数上限, 受 DB Admin 侧配额约束
  min: 2, // 常驻连接, 避免冷启动
  acquireTimeoutMillis: 3000, // 借不到连接的等待上限
  idleTimeoutMillis: 60_000, // 空闲连接回收
  testOnBorrow: true, // 借出前先校验
});
```

异常处理的所有策略, 都落在这三个函数和池参数的配合上。

## 异常一: 连接失败

场景: DB Admin 不可达 (网络故障、对端宕机、端口未监听), 或者认证握手被拒绝。此时 factory.create 抛错。

处理:

- create 内部带连接超时: net.connect 本身可能长时间挂起 (例如被防火墙丢包, 既不通也不拒), 必须设置 connectTimeout, 超时主动 destroy 并抛错, 不能无限等
- 区分错误类型: 认证失败 (配置错误) 重试没有意义, 应该快速失败并告警; 网络类错误 (ECONNREFUSED、超时) 可以交给池的重建机制
- 池层面的行为: create 失败后, generic-pool 会把等待中的 acquire 请求按策略处理; 排队方在 acquireTimeoutMillis 内拿不到连接就抛错, Koa 侧捕获后返回降级响应 (例如"DB Admin 暂时不可用"), 而不是让请求挂死
- 不要在 create 里做无限重试: 重试应该由池的按需重建 + 上层有限次重试组成, create 内部死循环重试会把池卡死

## 异常二: 请求超时

场景: 连接本身是通的, 但某次请求发出去之后 DB Admin 迟迟不响应 (对端负载高、请求卡住、中间链路丢包)。

处理:

- 请求级超时: 每次在连接上发请求都带超时计时, 超过阈值判定失败。超时和连接失败要分开统计, 前者说明对端处理能力问题, 后者说明连通性问题
- 超时后的连接处置是关键: 请求超时意味着这条连接上的协议状态已经不可信 (对端可能稍后才把迟到的响应发回来, 污染下一个借用者的请求), 正确做法是 destroy 这条连接, 让池补一条新的, 而不是归还复用
- 概括成一条原则: 任何让连接状态变得不确定的错误, 一律销毁, 绝不归还。只有明确"连接还干净"的场景 (例如业务层返回的错误码, 连接本身正常) 才归还
- 是否重试: 读类请求可以换一条连接重试一次; 写类请求要看 DB Admin 侧操作是否幂等, 不幂等就不能盲目重试, 避免重复执行

## 异常三: DB Admin 主动关闭连接

场景: DB Admin 侧有自己的空闲连接回收策略、例行重启、发布维护, 会主动关闭连接。JS 侧收到 socket 的 close 或 FIN。

处理:

- 连接上必须挂 error 和 close 事件监听: Node 的 socket 如果没有 error 监听器, 一次错误会直接抛未捕获异常打崩进程; 监听后把连接标记为不可用
- 池内感知: 连接被对端关闭后, 要么通过事件回调主动从池中驱逐 (pool.destroy), 要么依赖 testOnBorrow 在下次借出时用 ping 探活发现失效再销毁重建。两种机制并存时, 事件驱动是主路径, 探活是兜底
- 规避对端空闲回收: 如果 DB Admin 的空闲超时是已知的 (例如 5 分钟), 池的 idleTimeoutMillis 应该设置得比对端更短, 让己方先回收空闲连接, 减少"借到一条对端已经关掉的连接"的概率; 也可以发应用层心跳保活
- 半关闭的细节: 对端发 FIN 只表示它不再发数据, 己方如果还持有写方向, socket 不会立刻触发 close 而是进入半关闭; 因此判断连接可用性不能只看"socket 没报错", 要结合协议层 ping 的结果

## 异常四: 静默断开 (最隐蔽的一类)

场景: 中间网络设备重启、NAT 映射过期、链路丢包, 连接两端都没有收到 FIN/RST, 从 JS 侧看这条连接"一切正常", 直到下次写数据才发现不通, 或者请求发出去石沉大海。

处理:

- TCP keepalive: 开启 socket 的 keepalive 并设置较短的探测间隔, 让操作系统层面尽早发现死连接; 注意默认的两小时探测间隔在生产环境基本没有意义, 必须调短
- 应用层心跳: 比 keepalive 更可靠, 定期在协议层发 ping 并期待 pong, 连续 N 次无响应就判定连接死亡并驱逐。keepalive 只能证明链路存在, 心跳能证明对端的应用层还活着
- 请求超时兜底: 即使前两者都漏了, 请求级超时仍然能保证调用方不会永久挂起, 超时后按"状态不确定"原则销毁连接
- 三层防御的关系: keepalive 和心跳负责"提前发现死连接", 请求超时负责"出了问题也能止损", 缺一不可

## 异常处理的通用原则汇总

- 连接状态不确定就销毁: 超时、半关闭、写失败之后, 连接一律 destroy, 由池重建, 绝不把脏连接归还给下一个借用者
- 连接级错误与请求级错误分开: 业务错误码 (例如查询的表不存在) 不影响连接可用性, 正常归还; 传输层错误才触发销毁重建
- 池自动补位: 销毁连接后, 池根据 min 配置按需重建, 保证常驻容量; create 失败不会让池缩容到无法恢复
- 背压与快速失败: acquireTimeout + maxWaitingClients 控制排队规模, 池满时快速报错, 避免请求在队列里无限堆积拖垮 Koa
- 有限重试 + 幂等前提: 失败请求换连接重试一次, 写操作以幂等为前提; 重试风暴比对端宕机本身更危险
- 可观测性: 暴露池的借用等待时长、排队数、创建失败率、销毁原因分布, 连接池的问题大多是从指标异常开始的

## 与进程池方案的呼应

工作 2 的进程池隔离的是"C++ .so 崩溃"这类进程内风险, 工作 3 的 TCP 连接池管理的是"跨进程、跨机器的连接生命周期"风险。两者都用了 generic-pool, 但 factory 的语义完全不同: 前者的 worker 是子进程, 健康检查是进程存活; 后者的 worker 是 TCP 连接, 健康检查是协议层探活。池化模型是通用的, 异常处理策略必须贴着被池化资源的特性设计。
