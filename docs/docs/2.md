# ToD 数据链路: Kafka、Hive、ClickHouse、MySQL、Redis 的职责

## 背景与整体链路

ToD 项目使用 perfetto 在海量 Android 端设备侧采集设备性能数据. 设备侧采集的数据 (插桩慢函数、抓栈慢函数的采集结果) 上报后, 先落 Kafka, 再分发到 Hive、ClickHouse、MySQL、Redis 等多种存储, 后端从库中读取数据并提供 rpc 服务, 前端 BFF 层消费后渲染设备性能排行榜.

整体链路:

```
Android 设备侧采集 -> 上报网关 -> Kafka -> 消费任务分发
                                          -> Hive (离线全量)
                                          -> ClickHouse (实时聚合)
                                          -> MySQL (配置/元数据)
                                          -> Redis (热数据缓存)
                                          -> 后端 rpc 服务 -> BFF -> 前端页面
```

每个组件解决的是链路中不同性质的问题, 下面逐个分析.

## Kafka 数据接入与缓冲层

Kafka 是分布式消息队列, 在这条链路中充当数据接入层, 职责包括:

- 削峰填谷: 海量 Android 设备的上报流量存在明显的波峰波谷 (例如用户活跃时段), Kafka 先把数据持久化到 topic 中, 下游消费方按自己的处理能力匀速消费, 避免上报洪峰直接打垮数据库
- 解耦上报端与消费端: 设备侧只需要把数据写进 Kafka, 不需要知道下游有哪些存储; 后续新增一个存储 (例如再加一个分析库), 只需要新增一个消费组, 上报逻辑不用改
- 数据分发: 一份上报数据可以被多个消费组独立消费, 分别写入 Hive、ClickHouse 等不同存储, 这是"一份数据落多个库"的实现基础
- 可重放: Kafka 的数据按保留策略落盘保存, 如果某个下游消费任务出 bug 写错了数据, 可以重置消费位点重新消费、重新灌库

Kafka 在这里不承担查询职责, 它只是流动的管道, 真正的查询能力由后面的存储提供.

## Hive 离线数仓

Hive 是构建在 Hadoop 生态上的离线数仓, 用类 SQL (HiveQL) 查询存储在 HDFS 上的海量数据, 职责包括:

- 存全量历史数据: 设备性能数据量大且持续增长, Hive 依托 HDFS 可以低成本地存储 PB 级数据, 适合作为全量数据的"底座"
- 离线批量分析: 例如按机型、系统版本、App 版本维度做长周期的性能趋势分析、回溯分析, 这类查询对延迟不敏感, 但对数据全量性要求高
- 数据加工的上游: 可以在 Hive 上做 ETL, 把清洗、聚合后的结果再导出给在线库使用

Hive 的查询延迟是分钟级甚至更高, 不适合在线页面直接查询, 所以在线场景交给 ClickHouse 和 Redis.

## ClickHouse 实时分析库

ClickHouse 是列式存储的 OLAP 数据库, 在这条链路中承担在线可查的分析职责:

- 排行榜类聚合查询: 设备性能排行榜需要按机型聚合性能分、排序、分页, 这是典型的 group by + order by 场景; 列式存储只读取查询涉及的列, 配合向量化执行引擎, 可以在亿级数据上做到秒级甚至亚秒级响应
- 多维筛选分析: 前端页面支持按系统版本、App 版本、时间范围等维度筛选, ClickHouse 对这类宽表多维过滤 + 聚合的查询模式非常友好
- 数据压缩比高: 同一列的数据类型相同、取值相近, 列存压缩率远高于行存, 存储成本更低

ClickHouse 不擅长高频的单行更新和事务, 所以它只承接"写入后主要做聚合查询"的性能数据, 不存需要频繁修改的业务数据.

## MySQL 关系型业务数据

MySQL 是行式存储的事务型数据库 (OLTP), 在这条链路中存的是量不大但需要事务和关系建模的数据:

- 配置与元数据: 例如排行榜的配置、机型维表、采集任务的开关和参数等
- 需要事务保证的业务数据: 例如用户对某个榜单的订阅、标注等操作
- 点查场景: 按主键读取单条配置这类查询, MySQL 的索引点查又快又稳

性能明细数据不会放进 MySQL: 数据量级太大, 且聚合分析不是 OLTP 数据库的强项, 硬扛会把数据库拖垮.

## Redis 热数据缓存

Redis 是内存 KV 数据库, 在这条链路中是离数据库最近的一层缓存:

- 缓存热点查询结果: 排行榜头部数据、高频访问的机型聚合结果等放进 Redis, 请求直接命中内存, 不打到 ClickHouse / MySQL
- 降低数据库压力: 海量设备数据对应的查询 QPS 很高, 缓存层把大部分读流量挡掉, 数据库只承接缓存未命中的请求
- 支撑读多写少的场景: 性能榜单数据更新频率有限 (按批次刷新), 缓存失效策略简单, 命中率高

缓存之外, 后端进程内还有一层 lru 内存缓存, 与 Redis 组成多层缓存结构: 进程内 lru 命中则零网络开销, 未命中再查 Redis, 最后才落到数据库.

## 为什么需要这么多存储选型逻辑

本质是不同性质的数据、不同的读写模式, 没有一种存储能同时满足, 按职责拆开:

| 组件       | 类型      | 承接的数据             | 读写模式           | 延迟要求   |
| ---------- | --------- | ---------------------- | ------------------ | ---------- |
| Kafka      | 消息队列  | 流动中的上报数据       | 高吞吐写, 顺序消费 | 不直接查询 |
| Hive       | 离线数仓  | 全量历史明细           | 批量写, 离线分析   | 分钟级以上 |
| ClickHouse | 列式 OLAP | 性能明细数据           | 批量写, 聚合查询   | 秒级       |
| MySQL      | 行式 OLTP | 配置、元数据、业务数据 | 低频写, 点查, 事务 | 毫秒级     |
| Redis      | 内存 KV   | 热点查询结果           | 高频读, 低频写     | 亚毫秒级   |

选型逻辑可以概括为:

- 流量入口要能扛洪峰、能解耦、能重放 -> Kafka
- 全量历史数据要存得起、算得动 -> Hive
- 在线聚合分析要快 -> ClickHouse
- 小而精的关系型数据要事务和点查 -> MySQL
- 热点读流量要挡在数据库前面 -> Redis

## 与后端服务的衔接

后端 (Golang + Kitex 框架) 从上述存储读取数据, 进程内使用 lru 内存缓存进一步降低对 Redis 和数据库的访问, 对外通过 rpc 提供服务; BFF 层 (Nest.js) 调用 rpc 方法, 做数据清洗和整形后暴露 HTTP 接口给前端页面, 前端使用虚拟滚动列表渲染设备性能排行榜.

这样分层的收益: 每一层只处理自己擅长的负载, 任何一层的压力变化 (例如上报量翻倍、查询 QPS 翻倍) 都可以独立扩容, 不会互相拖垮.
